# 透明视图 · 生成档案 —— 交付说明

> 内容工厂 · 生成档案（Build Record）· WordPress 页面制作透明视图
> 目录：`E:/Shared_Project/seo/design_round/transparency/`

---

## 1. 这是什么

一个**单页交互视图**，把"AI SEO 内容工厂"造一座站的全过程摊开给客户看——
不是"AI 生成完直接交付"，而是**看着它被造出来、每一分怎么来的都留痕**。

它把一个种子词 `PU leather` 经过五个阶段变成一座 8 页互链的站，逐页可下钻：

- **① 主题簇**：1 个支柱页 + 7 个支撑页如何拆解、认领关键词、织成内链闭环。
- **② 关键词落位**：目标词落在标题/H2 或正文前 150 词/meta/正文密度四个槽位，命中标朱红、未命中标灰，正文密度带"理想 1–4 / >6 堆砌扣分"护栏。
- **③ 六维评分卡**：每页出厂前过一道满分 100 的确定性质检，<70 不出厂，逐维显示得分、规则注释、真实扣分点。
- **④ 上 WordPress**：忠实重现真实 REST 发布顺序（验证认证 → 幂等取/建分类 → 创建文章并注入 JSON-LD → 写 SEO meta 回读校验 → 固定链接检查）。
- **⑤ 结构化出厂**：注入 JSON-LD（Article / FAQPage / BreadcrumbList）、织内链图、列出 8 个出厂 URL，并**内嵌每页真实渲染的成品 HTML**（datasheet-editorial 主题）。

三种查看模式，同一份数据：

- **▤ 档案模式**（默认）：静态末态，全部可见，点任一页自由下钻。
- **▶ 重演模式**：按 `event_timeline` 定时重放整个生成过程（行式打印机读出窗），看它一步步被造出来。
- **▶| 实时生成模式**（Tier A 活预览构建）：分屏剧场——右屏成品页**逐块长出**、左屏关键词落位与六维质检**逐项点亮结算**，像 Canvas / Manus 式"看着页面被造出来"。详见 **§ 实时生成**。

视觉语言是"拼版台"：暖纸 `#F2EEE3` + 近黑墨 + 单一朱红 `#E2402A`，
中文巨标题走"得意黑"轮廓化 SVG（零 webfont 依赖、永不回落系统字）。

## ▶ 实时生成（Tier A 活预览构建）

模式开关里的 **▶| 实时生成**，是这份交付物的第三种看法，也是最"有戏"的一种。

### 它是什么

一个**分屏构建剧场**——点"生成"后，**右屏**的真实成品页按正文结构**逐块长出**
（标题 → 开头 → 各 H2 段落 → 表格 / 列表 …，带淡入、打字光标、扫描线），
每长出一块，**左屏**的两块仪表就对应点亮一格：

生成时左右两屏分开，本身就是这套透明视图的核心隐喻：**左屏是「数据·给搜索引擎」（DATA · FOR SEARCH ENGINES），右屏是「网页·给人」（PAGE · FOR HUMANS）**——
同一页内容长出来的瞬间，左边在算「机器读到的结构化信号」（关键词落位 + 六维质检），右边在长「人看到的成品页」，
中缝标注「两层权重」，正呼应一页内容同时要过的**两层权重**：既要让搜索引擎在结构化信号上读懂、给分，又要让人在阅读体验上读顺、信服。

- **关键词落位**：四个槽位（标题 +5 / H2 或开头 +4 / meta +3 / 正文密度 +3）随对应正文块
  出现而**逐槽点亮**，命中标朱红、未命中标灰，"已落位"分数一路累加。
- **六维质检**：六个维度的进度条**逐维收敛、逐维结算**，合计分朝门槛线（70）爬，
  到整页构建完时锁定本页**真实总分**并给出 ▸ PASS / ■ HOLD 判定。

像 Canvas / Manus 那种"看着 AI 把页面一笔一笔造出来"的体感——但这里造出来的是
**真实成品页**、点亮的是**真实评分**。**播完即末态**：和"档案模式"下钻到该页完全一致。
默认顺序播完全 8 页（pillar 起播），总进度条按"已构建块 / 全 8 页 213 块"跨页累计。

### 怎么用

1. 按第 2 节命令在本目录起 `http.server`，浏览器打开 `index.html`；
2. 顶部模式开关点 **▶| 实时生成**；
3. 用 transport 条操作：**▶ 生成**（自动逐块播）、**▶| 单步**（手动一块一块走，适合讲解）、
   **↻ 复位**（回第 1 页从头来）；播完后"生成"按钮变 **重播**。
4. 左屏徽标会从"待生成 / 待结算"→"落位中 / 结算中"→"已落位 / 已结算"，
   行式打印机读出窗同步读出"第 N 页 · 逐块长出 X / Y 块"。

> 终版截图见 `shots/splitlive-mid-1280.png`（构建到一半：右屏半成型 + 左屏部分点亮）、
> `shots/splitlive-done-1280.png`（末态：全落位 + 六维结算 + PASS）、
> `shots/splitlive-390.png`（移动端，分屏纵向堆叠）。

### 数据从哪来：record.json 的真实产出（**零 key、零 LLM、零网络**）

实时生成**不调用任何模型、不发任何请求、不需要任何 API key**。它放的全是**已经算好的真值**：

- 右屏逐块长出的，是 `output/<slug>.html` —— `render_samples.py` 真实渲染的成品页，
  前端只是把它的正文直接子块先隐藏、再按节奏逐块 reveal（**内容一字不改、不重新生成**）。
- 左屏点亮的关键词落位、收敛的六维分数，全部读自 `record.json` 的 `keyword_placement`
  与 `quality.breakdown`（即 `lib.quality.score_page` 的确定性产出）。
- **中途只显示 `··` 占位，绝不编造分数**：每个槽位 / 每个维度只在它"该结算"的进度点才落真值，
  在那之前显示占位符，避免给客户看一个不存在的中间分。末态收敛到的，就是档案里那个真实分。

一句话：实时生成是把"真实的最终产物"**演绎成一段构建过程**，戏是演的、**数全是真的**。

### 和「重演 / 档案」的区别

| | ▶ 重演 | ▶| 实时生成（Tier A） | ▤ 档案 |
|---|---|---|---|
| 推进单位 | `event_timeline` 事件（页级 / 阶段级） | **页内子步**（成品页正文逐块 reveal） | 无（静态末态） |
| 看点 | 整条管线一步步发生（行式打印机流水账） | **看着这一页被造出来 + 实时落位结算** | 全部可见、自由下钻 |
| 视觉 | 读出窗 + 阶段逐步点亮 | **分屏：右活预览 + 左实时仪表** | 完整五阶段 + 内嵌成品页 |
| 末态 | 播完 = 档案 | 播完 = 档案该页 | — |
| 数据 | record.json | record.json（同一份） | record.json（同一份） |

三者是**同一份 record.json 的三种叙事**，互不冲突：重演讲"管线全过程"、
实时生成讲"单页怎么长出来 + 分怎么结算"、档案给"末态自由下钻"。

### Tier B（真 token 流式）—— 需 key，为后续

当前的"实时生成"是 **Tier A：活预览构建**——演绎真实产物的构建过程，**零 key、可离线、可复算**，
适合做交付演示与客户讲解（绝不会因为没网 / 没额度而开天窗）。

**Tier B：真 token 流式生成**——接真实 LLM，正文**边生成边逐字吐字（SSE / streaming）**、
质检边写边算，是"真·实时"。它需要 **API key + 联网 + 额度**，且每次产出会随模型微变
（不再逐字节可复算）。Tier B 属**后续增强项**，不在本交付物范围内；落地时会复用本剧场的
分屏 UI（右活预览 + 左实时仪表），把"逐块 reveal 真值"换成"逐 token 写入真生成"。

## Stage 00 · 词怎么来的（关键词溯源视图 `keywords.html`）

这是**生成档案之前的那一站**。生成档案（`index.html`）回答"页面怎么造出来的"，
而 Stage 00 回答更上游、客户最常质疑的一问——**"这些关键词是 AI 凭空想的吗？"**
答案是：不是。`keywords.html` 把选词的全过程摊开给客户看。

### 它讲什么

一个种子词 `PU leather`，**真的去敲 Google / Bing 的搜索框**，把搜索引擎给出的
**真实下拉补全建议**收回来，按**搜索意图分层**，再聚成一张**每页都有出处**的站点计划。
三段对应数据里的三块：

- **§A 采集 harvest**：行式打印机读出窗（`queries_fired` 实打查询）+ 账本
  （每条查询返回了哪些补全、源是 Google 还是 Bing）。这些词不是模型脑补，是搜索引擎
  根据千万真实用户输入给出的补全。
- **§B 分层 intent**：词池按意图分桶（对比 / 应用 / 商业 / 信息 / 其它），看清同一种子
  背后藏着不同需求的人。计数全部来自 `intents[*].count`。
- **§C 聚类 plan**：把真实需求聚类成页面，每页认领一个真实 `target_keyword`，
  并列出**支撑它的真实查询**（`evidence` 出处）。第一行是 pillar 支柱页。

底色一句话：**确定性 · 真实搜索 · 零 LLM · 有出处 · 可复算**。

### 怎么打开

和生成档案一样，通过 `fetch()` 读 `keyword_record.json` / `svg.json`，**不能双击
`file://` 打开**，必须本地 HTTP 托管。在**本目录**起服务：

```powershell
python -m http.server 8792 --directory E:/Shared_Project/seo/design_round/transparency
```

浏览器打开：

```
http://127.0.0.1:8792/keywords.html
```

> 终版截图见 `shots/stage00-keywords-1280.png`（桌面）与 `shots/stage00-keywords-390.png`（移动）。

### 数据从哪来：`keyword_record.json`

视图里**一个词都不编造**，全部映射自同目录 `keyword_record.json`。这份 JSON 由
关键词研究 agent 真实跑出来，两条等价入口：

```powershell
# 入口一:跑整条管线的接地规划(会顺带写出 keyword_record.json)
python E:/Shared_Project/seo/run.py <config> --grounded

# 入口二:单独调用工具层(纯 Python、model 无关)
#   lib/keyword_scout.py —— grounded_plan(seed) → write_record()
```

`--grounded` 触发 `run.py` 里的 `plan_pages(grounded=True)` → 调
`lib/keyword_scout.py` 的 `grounded_plan(seed)`，再 `write_record()` 落盘
`keyword_record.json`。工具层做的是：

- `google_autocomplete()` 打 `suggestqueries.google.com`、`bing_autocomplete()` 打
  `api.bing.com/osjson.aspx` 抓**真实补全**（带磁盘缓存，礼貌限速）；
- `classify_intent()` 按**确定性规则**分意图（非 LLM）；
- `cluster_plan()` 去重、过滤跑题长尾、聚类成 pillar + cluster 页面计划。

整条**确定性、无 LLM**：补全样本可能随搜索引擎当日数据微变，但分层与规划逻辑
对同一份补全输入永远产出同一结果，可复算、可追溯。

### 它和「生成档案 `index.html`」的关系

**同一个种子 `PU leather`，前后两站，不重复也不冲突：**

| | Stage 00 · 关键词溯源 `keywords.html` | 生成档案 `index.html` |
|---|---|---|
| 回答 | **词怎么来的**（选词） | **页面怎么造的**（造页） |
| 数据 | `keyword_record.json` | `record.json` |
| 内容 | harvest · intent · plan（接地发现） | 主题簇 · 落位 · 评分 · 上 WP · 出厂 |
| 共性 | 同种子、同视觉语言（拼版台）、同 pillar、零 LLM、可复算 | 同上 |

两者是**承接关系而非逐页一一对应**：Stage 00 是同一种子的接地发现（讲选词的来路），
生成档案是把这些词喂给生成管线后造出的成品（讲造页的过程）。`keywords.html` 封口处
直接链向 `./index.html`（"这些词将喂给生成管线产出页面 → 见 生成档案 · Build Record"），
形成"选词 → 造页"的完整透明叙事。

## 4. 哪些是真数据，哪些是演示重现

**这是这份交付物最重要的一条诚实红线，请如实向客户说明。**

### 真数据（来自 `lib/quality.py`，确定性 · 无 LLM · 可复算）

- **六维评分**：`keyword_usage / structure / depth_wordcount / internal_links /
  specificity_antislop / meta_title_quality`，合计 100 分，门槛 70。
  逐页、逐维的分数、规则注释、扣分点全部由 `lib.quality.score_page()` 真实算出，
  视图里**一个数字都不编造**，都来自 `./record.json`。
- **关键词落位图**：四个槽位（权重 5/4/3/3）的命中判定逐字复用 `quality.py` 的
  `_keyword_in / _count_keyword / _heading_texts / strip_html`，与评分卡里的
  `keyword_usage` 维度判据完全一致。`<mark>` 高亮的是正文里真实存在的句子片段。
- **JSON-LD 结构化数据**：由 `lib/schema.py` 的 `jsonld_for()` 真实生成
  （Article / FAQPage / BreadcrumbList）。
- **内嵌成品页**：`output/<slug>.html` 是 `render_samples.py` 真实渲染的产物
  （datasheet-editorial 主题），不是截图、不是占位。

### 演示重现（"上 WordPress"段 · 未连真站）

- **④ 上 WordPress** 阶段展示的 REST 请求顺序、POST body 摘要、SEO meta 字段、
  各项检查结果，是**演示数据下对真实发布动作的忠实重现**——它镜像
  `lib/wp_publish.py` + `run.py` 的真实发布逻辑与顺序，但**没有连任何真实 WordPress 站**。
  视图里有醒目朱红徽带「演示数据 · 未连真站」明确标注，封口处也再次声明。
- 时间戳：record.json 里**不写真实时间戳**（用固定占位日期 `2026-01-01`），
  保证每次重跑 `build_record.py` 产出完全一致、可复算。

## 6. 如何重新生成

整条管线**确定性、无 LLM、无网络**，可随时复算。

### 6.1 重渲成品页（升级主题后）

主题升级（`lib/themes/datasheet.py` 等）或内容改动后，先重渲成品页：

```powershell
python E:/Shared_Project/seo/render_samples.py
```

产出刷新到 `E:/Shared_Project/seo/output/<slug>.html`。

### 6.2 重建生成档案数据脊柱

```powershell
python E:/Shared_Project/seo/design_round/transparency/build_record.py
```

它会：

1. 读 `industries/pu-leather.yaml` 的 8 页结构 + `output_src/<slug>.json` 的真内容；
2. 跑 `lib.quality.score_page`（六维评分）+ `lib.schema.jsonld_for`（JSON-LD）；
3. 算关键词落位图、拼 wp_publish 演示载荷、铺 `event_timeline`；
4. **把 `output/<slug>.html` 镜像进 `transparency/output/`**（让本目录自包含）；
5. 写出 `record.json`。

### 6.3 重生成中文巨标题 SVG（仅在改文案/字体时）

```powershell
python E:/Shared_Project/seo/design_round/transparency/gen_svg_transparency.py
```

把固定 display 文案用"得意黑"轮廓化为内联 SVG，产出 `svg.json`。
（依赖 `fontTools` 与 `design_round/fonts/SmileySans-Oblique.ttf`。）

### 6.4 重生成单文件「生成档案.html」

`build_record.py` 之后，若 `record.json` / `svg.json` 有更新，重跑内联脚本即可刷新单文件：

```powershell
python E:/Shared_Project/seo/design_round/transparency/inline_single.py
```
